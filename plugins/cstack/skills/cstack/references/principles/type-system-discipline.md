# Discipline du système de types

Lisez cette référence lorsqu'un processus cstack actif vous route ici ou lorsque l'utilisateur nomme ce principe. Suivez le [contrat d'exécution Codex](../codex-runtime.md) pour le périmètre et les permissions.

Le vérificateur de types est un assistant de preuve. Utilisez-le pour éliminer à la compilation les états impossibles, les primitives incompatibles et les variantes non gérées. Un cas que les types vous laissent ignorer devient une erreur à l'exécution que le compilateur aurait pu arrêter. Préférez rendre erreurs et cas spéciaux inexistants par définition plutôt que multiplier les gestionnaires. Les états irreprésentables, fonctions totales et refontes d'interface (les motifs ci-dessous) sont les outils.

S'applique à tout langage typé. Des compétences comme `typescript-best-practices` l'ancrent dans une syntaxe précise.

**Les motifs :**

- **Rendre les états illégaux irreprésentables.** Modélisez les variantes comme des types somme : unions discriminées en TypeScript, enums avec charges utiles en Rust/Swift/Kotlin, sealed classes en Scala, ADT en Haskell/OCaml. Ne modélisez pas l'état comme un sac de champs optionnels où des combinaisons contradictoires compilent. Anti-motif subtil : `{ completed: boolean; completedAt?: Date }` admet `completed: true; completedAt: undefined`, ce qui n'a pas de sens. Dérivez le booléen depuis une seule source comme `completedAt !== null`, ou modélisez explicitement les variantes comme `{ kind: 'open' } | { kind: 'done'; at: Date }`. Si une anomalie force la question « attends, cette combinaison peut-elle vraiment arriver ? », le type est trop lâche.
- **Les types sont des constructions, pas des restrictions.** Construisez le type à partir des valeurs que vous voulez plutôt que de les tailler dans un type plus lâche avec des contrôles. L'invariant qui semble nécessiter un type raffiné n'est souvent qu'à une construction de distance. Une liste non vide est une tête plus un reste, pas une liste avec un contrôle de longueur. Une plage de temps valide est un début plus une durée, pas deux timestamps que vous devez garder ordonnés. Aucune représentation n'est privilégiée. Une liste de paires est une liste de longueur paire si vous l'interprétez ainsi, donc choisissez la forme qui ne peut pas construire la valeur illégale et exposez par-dessus l'interface dont les appelants ont besoin.
- **Marquez les primitives sémantiques.** `UserId` et `OrderId` sont des chaînes dessous mais ne doivent pas être interchangeables. Newtypes en Rust, types opaques en Swift, value classes en Kotlin, phantom types en Haskell, intersections brandées en TypeScript. Validez une fois à la création, faites confiance au type en aval.
- **Les données externes sont non typées jusqu'à l'analyse.** Charges utiles RPC, JSON, messages IPC, arguments CLI, fichiers de config, variables d'environnement, lignes de base de données. Ayez une fonction d'analyse à chaque frontière qui transforme l'entrée non structurée en modèle typé. Voir la référence de principe [Discipline des frontières](boundary-discipline.md) pour savoir où placer la validation.
- **Ne mentez pas au système de types.** Les casts, coercitions unsafe et fonctions d'assertion qui contournent le compilateur sont des plantages à l'exécution latents. Si le compilateur ne peut pas prouver un fait, prouvez-le (valider, rétrécir, raffiner le modèle) ou acceptez que le cast est un risque.
- **La correspondance exhaustive est le travail du compilateur.** Quand vous faites une correspondance sur un type somme, le compilateur doit échouer à compiler si une nouvelle variante est ajoutée sans gestionnaire. Utilisez l'idiome fourni par votre langage : liaison typée `never` en TypeScript, `match` non annoté en Rust, `-Wincomplete-patterns` en Haskell, exhaustivité de correspondance des classes scellées en Kotlin.
- **Dérivez les types depuis les schémas autoritaires.** Quand un protocol buffer, une spec OpenAPI, un schéma GraphQL, une migration de base de données ou un fichier de tokens de système de conception définit une forme, dérivez-en le type au lieu d'écrire à la main un type parallèle. Voir la référence de principe [Encoder les leçons dans la structure](encode-lessons-in-structure.md).
- **Renforcez un type seulement là où la partialité apparaît.** Une assertion à l'exécution, un contrôle null ou un throw « ceci ne devrait jamais arriver » marque l'endroit où un type est trop faible. Poussez ce contrôle dans le type. Puis arrêtez. Le travail du système de types est de suivre les cas que chaque site d'utilisation doit gérer, pas de décrire les données aussi précisément que possible. Préférez les fonctions totales. `sum` d'une liste vide vaut 0, donc elle prend la liste simple. `head` d'une liste vide n'a pas de réponse, donc elle exige la liste non vide.

**Les tests :**

- « Puis-je écrire un commentaire expliquant quand cette combinaison de champs est valide ? » Si oui, le type est trop lâche. Séparez-le en type somme.
- « Deux arguments de ma fonction partagent-ils un type primitif mais signifient-ils des choses différentes ? » Brandez-les.
- « D'où viennent ce `any`, ce `as`, ce `assertNotNull` ? » Remontez-le jusqu'à la frontière et validez là plutôt.
- « Si une nouvelle variante est ajoutée le mois prochain, le compilateur dira-t-il au prochain agent où ajouter un cas ? » Sinon, le match n'est pas exhaustif.
- « Ce type duplique-t-il une forme possédée par un autre fichier ? » Dérivez plutôt.
- « Est-ce que je renforce ce type pour garder une opération totale, ou seulement pour être plus précis ? » Si rien ne paniquerait autrement, gardez le type simple.
