# Limites de plateforme

Les webhooks Grok Bot et le pack Benny événementiel de Cursor n’ont pas d’implémentation de remplacement direct ici. Leurs notices pointent vers la source originale ; ils ne sont pas activés silencieusement. Une investigation manuelle équivalente de bug peut utiliser les outils Codex disponibles sans revendiquer un service webhook.

Le plugin livre deux hooks, l’équivalent du `reminder:` de pstack : après `$cstack:cstack`, `UserPromptSubmit` rappelle le mode à chaque message et `SessionStart` (`compact`, `resume`) renvoie aux [règles communes](base.md) et au point de reprise de la tâche active ([état](etat.md)) après un résumé ; ailleurs, ils se taisent. `PreCompact` n'est pas utilisé : Codex n'y accepte aucun champ qui oriente le résumé, seulement un avertissement affiché. Codex les ignore tant que l’utilisateur ne les a pas approuvés une fois (`/hooks` dans Codex CLI ; voir le guide de setup, section « Rappel du mode ») ; sans eux, cstack fonctionne sans rappel. Une compétence choisie au sélecteur sans `$cstack:cstack` dans le texte n’active le rappel qu’au premier message qui le contient.

Un plugin Codex ne livre pas d’agents : les agents custom se déclarent en TOML par projet (`.codex/agents/`) ou par utilisateur. `$cstack:setup-cstack` peut écrire les trois agents projet `cstack-*` avec les choix acceptés ; il n’installe jamais de rôle global. Un agent déclaré n’est pas la condition d’une délégation ; les types génériques exposés par l’hôte suffisent. La documentation Codex affirme que l’hôte respecte les consignes de délégation d’`AGENTS.md` ou d’une compétence : les sessions observées ci-dessous avaient les deux, donc ni l’un ni l’autre n’est mesuré seul, et le bloc `AGENTS.md` du setup porte aussi cette demande.

La vraie contrainte est ailleurs : l’hôte ne lance un sous-agent que sur demande explicite. Mesuré dans `docs/evidence/0.3.0.json` : sur treize scénarios, les quatre qui ont lancé des enfants portaient tous une demande de délégation dans la demande utilisateur, et aucun autre n’en a lancé. Mesuré dans `docs/evidence/delegation-host-observations.json` : la consigne `multi_agent_mode` de l’hôte accepte une demande de l’utilisateur, d’un `AGENTS.md` applicable ou des instructions d’une compétence, et quatre sessions Codex Desktop et T3 Code ont lancé de 9 à 18 enfants sur une invocation de `$cstack:cstack` sans aucun mot de délégation dans le message. La demande n’a donc pas à figurer dans le tour de l’utilisateur. Ces sessions chargeaient aussi un `AGENTS.md` qui demandait des sous-agents natifs : l’effet du texte d’une compétence seul reste non mesuré. Les messages T3 observés portent `$cstack:<skill> <demande>` sans le `default_prompt`. Non mesuré : `codex exec` et les versions ultérieures de l’hôte.

Écris cette demande dans le corps du SKILL.md de toute compétence qui délègue, puisque l’hôte accepte les instructions d’une compétence et que le `default_prompt` n’atteint pas toujours le message ; garde-la aussi dans le `default_prompt`. Ne la retire d’aucun des deux en reformulant. Quand un utilisateur signale qu’un seul acteur travaille, vérifie d’abord cette demande, puis la configuration d’agents de l’hôte et sa limite de threads simultanés, avant de conclure à un défaut de routage.

Un délégué ne lance pas de descendants sauf si son parent lui délègue explicitement cette décision ; c’est la règle de `../agents/cstack-agent.md`, pas une limite de plateforme. Une compétence qui ventile doit donc s’exécuter dans la session qui possède la ventilation ; la déléguer entière coûte sa propre ventilation. Ventile les tranches, pas les compétences qui ventilent. Quand cette règle rencontre une orchestration requise, applique [Orchestration requise](orchestration.md).

Voir la [documentation officielle des sous-agents](https://learn.chatgpt.com/docs/agent-configuration/subagents) et le [contrat de packaging de plugin](https://developers.openai.com/plugins/build/plugins).
